===============================================================================
2.  INSIGHTS - WHAT WAS LEARNT, AND THE DECISIONS IT DROVE
===============================================================================

This application succeeds the ESL PMO Tracker. That build and its
implementation log recorded a series of defects and deployment traps. Each is
closed here by design, not by patch. They are listed because they are the
things most likely to be "helpfully" reintroduced later.

2.1  Business-unit data leaked across units            -> closed at the data layer
     In the ESL tracker no screen filtered by business unit: every user saw
     every unit, and an ESL PMO could approve IOB's actuals. Here the user's
     visible units ("scope") are computed ONCE per request and every database
     query filters on it. A query called without scope returns nothing, so a
     mistake shows as an empty screen, never as another unit's figures.

2.2  "Plan achievement 396.8%"                          -> ratios carry their basis
     Three months of actuals were divided by one month of plan. Now a
     percentage can only be built by one function that returns the numerator,
     denominator, basis and window together, and every tile prints its basis.
     Two different figures are shown side by side and labelled:
       Achievement (plan-to-date) = booked / plan, closed months only
       Target delivered (full year) = booked / full-year target

2.3  Consolidated totals multiplied ("fan-out")         -> separate aggregation passes
     A view joined initiatives to monthly totals and repeated each total once
     per initiative (VISL plan 670 Cr against a 105 Cr target). Counts and
     money are now aggregated separately and joined 1:1 per unit, and a
     reconciliation gate checks every parent equals the sum of its children.

2.4  Initiatives on roll-up nodes double count          -> leaf-only rule, 3 layers
     Initiatives may only belong to ESL, IOK, IOG, VAB, HO or FACOR - never to
     VISL or IOB. Enforced in code, in the API and by a database CHECK.

2.5  Only approved actuals count                        -> governance as arithmetic
     draft -> submitted -> approved. "Booked" = approved only. Submitted is
     shown separately as pipeline. An approved month is locked; reopening it
     is an explicit, audited act. Nobody can approve their own submission.

2.6  Deployment traps from the ESL setup                -> written into the scripts
     - dotenv silently cuts a value at '#': the DB password "failed" for half
       a day. RULE: secrets use only letters, digits, hyphen, underscore.
     - Error 916 / empty sys.tables: sessions sitting on master. The migrator
       refuses to run unless connected to the named database.
     - Seed aborted on a bad CSV and left no admin: the admin password is now
       set by a separate step that a bad data file cannot affect.
     - Department name collisions across units: names are unit-qualified,
       e.g. "Commercial (IOK)".
     - Serverless Azure auto-pause made the first click take a minute:
       timeouts raised; provisioned tier / on-prem recommended.
     - Hard-coded server path in the PM2 config: resolved at runtime.

2.7  Defects found and fixed during the September 2026 review
     - Bulk approve/return never worked (route order). Fixed.
     - SQL mode: queries selected the same column twice, which the driver
       returns as an array; every dashboard would have read zero. Fixed, and
       all SQL DATE values are now normalised to 'YYYY-MM-DD'.
     - Milestones table lacked two columns the code writes. Fixed + upgrade.
     - Users created in the admin screen had no way to sign in on the real
       database (no password field, no AD flag). Fixed: sign-in method +
       password on the form.
     - Initiative codes could collide after a CSV load. Fixed.
     - CSV month headings: "Apr-26" and "Apr 26" both accepted now.
     - Plan-vs-booked bars on the initiative list never rendered. Fixed.

2.8  Design principles worth keeping
     - Active Directory proves WHO you are; this application decides WHAT you
       may see. AD never grants access by itself.
     - The route layer never knows which database it talks to (synthetic or
       SQL Server). The whole system can be demonstrated with no database.
     - Mail is reviewable before it is sent ("outbox mode" is the default).
     - Nothing is loaded from the internet at runtime (plant networks).

3.  THE BUSINESS MODEL
===============================================================================

3.1  VOCABULARY
  Target            Full-year commitment of an initiative (Rs Cr).
  Plan              The target spread over 12 months (Apr-Mar). Must foot to target.
  Actual            The saving an owner reports for a month.
  Booked / Banked   APPROVED actuals only. This is "the savings number".
  Pipeline          Submitted, awaiting approval. Real work, not yet counted.
  Closed month      Settled for reporting (setting reporting.closed_through).
  Collection month  The month owners are entering now (reporting.submission_period).
  Variance          Booked minus plan. Negative early in a month is usually timing.
  Forecast FY       Booked to date + plan for the months still open.
  Unplanned gap     Target not covered by booked + pipeline + remaining plan.

3.2  FORMULAS (all in src/domain/metrics.js; mirrored in sql/03_views.sql)
  plan_ptd          = sum(plan)   over closed months
  booked_ptd        = sum(actual where approved) over closed months
  achievement_ptd   = booked_ptd / plan_ptd          (null if plan_ptd = 0)
  target_delivered  = booked_fy / target             (booked, all months)
  forecast_fy       = booked_fy + plan of open months
  Money is carried at 4 decimals and rounded to 2 only for display.

3.3  THE MONTHLY CYCLE
  1st        PMO sets System > Reporting calendar > Collection month.
  1st        Submission reminders go out (or run from Mail outbox).
  1st-7th    Owners enter actuals on "My work" and submit.
  5th-10th   Approvers work the Approvals queue (approve / return with reason).
  10th       PMO moves "Closed through" forward - this publishes the month.
  10th       Run npm run check:metrics and sql/04_verify.sql.
  11th       Executive board reflects the closed month; print the board pack.

3.4  APPROVAL POLICY (System > Approval policy - a setting, not code)
                   IOK/IOG/VAB/HO approved by   ESL approved by   FACOR approved by
  local            that unit's own PMO           ESL PMO           FACOR PMO
  central (default) IOB PMO                      VISL PMO          VISL PMO
  visl             VISL PMO                      VISL PMO          VISL PMO
  Maker-checker: nobody approves an entry they submitted (any role).

5.  ACCESS PROVISIONS
===============================================================================

5.1  ROLES
  admin        All units. Everything, incl. users and system settings.
  visl_pmo     All units. Full governance (create, edit, approve, reopen).
  visl_exec    All units, READ-ONLY. CEO, CFO, business heads.
  bu_pmo       Home unit + units beneath it. Governs and approves there.
  owner        Home unit. Their own initiatives: plan, actuals, tasks, risks.
  contributor  Home unit. Works assigned tasks, comments.
  viewer       Home unit, READ-ONLY.

5.2  SCOPE = HOME BUSINESS UNIT + EVERYTHING BENEATH IT
  Home VISL + global role   sees VISL, ESL, IOB, IOK, IOG, VAB, HO, FACOR
  Home IOB  + bu_pmo        sees IOB, IOK, IOG, VAB, HO
  Home ESL  + bu_pmo        sees ESL
  Home IOK  + owner         sees IOK
  Writes are only ever against reporting units (never VISL or IOB).

5.3  PERMISSION MATRIX            admin visl_pmo visl_exec bu_pmo owner contrib viewer
  view initiatives / reports        x      x        x        x      x      x      x
  export to Excel                   x      x        x        x      x
  comment                           x      x        x        x      x      x
  update assigned tasks             x      x                 x      x      x
  edit own initiative/plan/actuals  x                               x
  create / edit any initiative      x      x                 x
  edit any plan, submit any actual  x      x                 x
  approve / reopen actuals          x      x                 x
  manage tasks & risks (any)        x      x                 x
  audit trail                       x      x                 x
  mail outbox                       x      x
  users & system settings           x
  The live matrix is at Administration > Access model.

5.4  PROVISIONING A USER (Administration > Users & roles > Add user)
  1. User ID: for AD users, their Windows logon name (sAMAccountName) EXACTLY
     as in AD, e.g. kumud.kesar.
  2. Name, email, designation.
  3. Role and home business unit (the preview shows what they will see).
     The home unit also decides WHICH DIRECTORY they sign in against:
       ESL                              -> ESL directory
       IOB, IOK, IOG, VAB, HO, FACOR    -> IOB directory
       VISL (group-level)               -> ESL tried first, then IOB
  4. Sign-in method:
       Active Directory  - no password stored; they use their AD password.
       Local password    - for break-glass / service accounts; 10+ chars.
  5. Save. The user can sign in immediately.
  A valid AD password alone grants nothing: the account must exist here,
  be active, and be marked Active Directory. Nobody is auto-created.
  Leavers: untick "Account is active" (their AD account being disabled also
  blocks sign-in).

5.5  BREAK-GLASS ADMINISTRATOR
  sql/02 creates "pmo.admin" (local, no password). Set its password with
     npm run seed -- --admin pmo.admin --password <<10+ chars>>
  Run with AUTH_MODE=hybrid so this local admin still works if both
  directories are down. Keep its password in the company vault.

===============================================================================
8.  SQL SERVER (SSMS) - ARCHITECTURE AND STEP-BY-STEP SETUP
===============================================================================

8.1  TARGET ARCHITECTURE
  - SQL Server 2019 or 2022 (2016 SP1 minimum - STRING_SPLIT is required),
    any edition incl. Standard. Azure SQL Database also supported (8.12).
  - A dedicated database VISL_PMO. Preferably NOT on a server that hosts
    unrelated production systems (the ESL database sat on a shared IOB BI
    server - flagged as a risk). A dedicated instance or at least its own
    backup/lifecycle policy.
  - Two SQL logins, least privilege (created by sql/00_server_setup.sql):
        visl_owner  db_owner on VISL_PMO only  - schema changes, run by DBA
        visl_app    db_datareader + db_datawriter - what the app uses at runtime
    Optional third: visl_report (db_datareader) for Power BI.
  - Recovery model FULL with log backups; READ_COMMITTED_SNAPSHOT ON.
  - Network: TCP 1433 (or the instance's fixed port) open ONLY from the
    application server. Encryption on (Force Encryption or client-requested).
  - Size: small. < 1 GB for years of data. 2 vCPU / 4-8 GB RAM instance is
    plenty; the application holds at most 10 connections (DB_POOL_MAX).

8.2  PREREQUISITES ON THE SQL SERVER (DBA)
  a. Server authentication = "SQL Server and Windows Authentication mode"
     (SSMS > server > Properties > Security). Restart the service if changed.
     If policy forbids SQL logins, use a domain service account instead:
     see 8.11.
  b. TCP/IP enabled (SQL Server Configuration Manager > Network
     Configuration > Protocols > TCP/IP = Enabled; restart).
  c. Named instance: give it a FIXED port (TCP/IP > IP Addresses > IPAll >
     TCP Port, clear "TCP Dynamic Ports") - simplest to firewall. Otherwise
     SQL Browser (UDP 1434) must also be reachable.
  d. Windows Firewall inbound rule: TCP <<port>> from <<app server IP>> only.
  e. A certificate for encryption: either one issued by the company CA to the
     server's FQDN (preferred - set DB_TRUST_SERVER_CERT=false), or the
     default self-signed certificate (set DB_TRUST_SERVER_CERT=true; an
     accepted internal-network risk, record it).

8.3  STEP 1 - CREATE THE DATABASE AND LOGINS  (DBA, SSMS, as sysadmin, on master)
  Open sql/00_server_setup.sql. Replace <<OWNER_PASSWORD>> and
  <<APP_PASSWORD>> (16+ chars; letters, digits, - and _ only). Adjust
  COMPATIBILITY_LEVEL (160 for 2022, 150 for 2019, 130 for 2016) and any
  file/backup paths. Execute PART A. The last result grid must show:
        visl_app    db_datareader
        visl_app    db_datawriter
        visl_owner  db_owner

8.4  STEP 2 - CREATE THE SCHEMA  (DBA, SSMS, connected AS visl_owner)
  In SSMS: Connect > Options > Connection Properties > "Connect to database"
  = VISL_PMO (this avoids error 916 and the "empty sys.tables on master" trap).
  Then open and execute IN ORDER, confirming SELECT DB_NAME() = VISL_PMO first:
        sql/01_schema.sql           tables, constraints, indexes
        sql/02_reference_data.sql   business units, levers, settings, pmo.admin
        sql/03_views.sql            the six consolidation views
        sql/04_verify.sql           checks - every section must show OK
  Each script is idempotent: safe to re-run. Files contain GO separators -
  run each file as a whole in SSMS (F5).
  Alternative from the app server: set DB_USER=visl_owner temporarily in
  .env, run  npm run migrate  (runs 01-04, stops at the first error and
  prints the failing batch), then set DB_USER back to visl_app.

8.5  STEP 3 - DEPARTMENTS  (PMO provides the list; DBA runs it)
  Edit sql/05_departments.sql: replace the sample rows with the real
  departments per reporting unit, names qualified with the unit, e.g.
  N'Commercial (IOK)'. Execute against VISL_PMO. The guard query must
  return no rows. Re-run any time the list changes (never deletes).

8.6  STEP 4 - CONNECT THE APPLICATION (IT, on the app server - see 11)
  In .env:
        DATA_MODE=mssql
        DB_HOST=<<server FQDN, without \instance>>
        DB_INSTANCE=<<instance name, or blank for default instance>>
        DB_PORT=<<1433 or fixed port; ignored when DB_INSTANCE is set>>
        DB_NAME=VISL_PMO
        DB_AUTH=sql
        DB_USER=visl_app
        DB_PASSWORD=<<APP_PASSWORD>>
        DB_ENCRYPT=true
        DB_TRUST_SERVER_CERT=<<false with CA cert | true with self-signed>>
  What you type in SSMS "Server name" maps like this:
        SQLPRD01                   DB_HOST=SQLPRD01           DB_INSTANCE=
        SQLPRD01\VISL              DB_HOST=SQLPRD01           DB_INSTANCE=VISL
        SQLPRD01,14330             DB_HOST=SQLPRD01           DB_PORT=14330
        sqlprd01.vedanta.local     DB_HOST=sqlprd01.vedanta.local

8.13 SQL TROUBLESHOOTING
  Login failed for user 'visl_app' (18456)
      State 5: login does not exist. State 8: wrong password - check for #, $
      or quotes in DB_PASSWORD (dotenv truncates at #). State 38 / 4060: the
      login has no user in VISL_PMO - re-run sql/00 A3. State 58: server is in
      Windows-only mode - see 8.2a.
  Error 916 "cannot access database master"   the connection did not name the
      database - DB_NAME must be set; in SSMS set Connect to database.
  "Failed to connect ... in 15000ms" / ETIMEOUT   firewall, wrong port, TCP/IP
      disabled, or named instance without SQL Browser - see 8.2 b-d.
  "self signed certificate" / "certificate verify failed"   set
      DB_TRUST_SERVER_CERT=true, or install a CA-issued cert on SQL Server.
  "Invalid object name 'dbo.vw_...'"   views missing - run sql/03, then 04.
  "The SELECT permission was denied"   visl_app lacks db_datareader - sql/00 A3.
  "CREATE TABLE permission denied" during npm run migrate   you are running as
      visl_app; migrations need visl_owner (8.4).
  STRING_SPLIT is not a recognized built-in function   compatibility level
      below 130 - ALTER DATABASE VISL_PMO SET COMPATIBILITY_LEVEL = 150.
  Dashboards all zero   check System > Reporting calendar: if Closed through
      is before the first approved month, zero is correct.
  A parent total does not equal its children   run sql/04_verify.sql
      sections 3-4; an initiative on a roll-up node is the usual cause.

9.  ACTIVE DIRECTORY OVER LDAP - TWO DIRECTORIES
===============================================================================

9.1  LDAP IN PLAIN WORDS
  Active Directory (AD) is the company's list of people and their passwords.
  LDAP is the language applications use to talk to it. For sign-in, the
  application needs only two LDAP operations:
    - SEARCH  "find the person whose logon name is kumud.kesar" -> returns
              their Distinguished Name (DN), the full address of their entry,
              e.g. CN=Kumud Kesar,OU=Users,OU=IOB,DC=iob,DC=local
    - BIND    "log in to the directory as <DN> with <password>". If AD accepts
              the bind, the password is correct. That is the whole check.
  Key terms
    Domain controller (DC)  the server that answers LDAP (e.g. iob-dc01)
    Base DN                 where to search, e.g. DC=iob,DC=local
    sAMAccountName          the Windows logon name (kumud.kesar)
    Service account         a read-only AD account the app uses to SEARCH
    LDAPS                   LDAP over TLS on TCP 636 - encrypted from the start
    StartTLS                LDAP on TCP 389 upgraded to TLS before anything is sent
    Root CA certificate     lets the app trust the DC's LDAPS certificate

9.2  VISL TOPOLOGY - TWO DIRECTORIES
        ESL directory   serves home unit ESL
        IOB directory   serves IOB, IOK, IOG, VAB, HO **and FACOR**
  Each user signs in against the directory of their home business unit.
  Only that directory is tried, so the same logon name existing in both
  forests can never be confused. Group-level users (home unit VISL) are
  tried against ESL, then IOB (order of AD_DIRS); the first that accepts wins.
  If group-level staff all sit in one forest, list it first in AD_DIRS.

9.3  WHAT HAPPENS AT SIGN-IN
   Browser --(user ID + password, over HTTPS)--> Application
   1. Application finds the user in dbo.users: must exist, be active and be
      an AD account (ad_user = 1). Otherwise: "Incorrect user ID or password".
   2. Picks the directory from their home unit (9.2).
   3. Opens LDAPS to that DC (verifies its certificate against the CA file).
   4. BINDs as the service account; SEARCHes the base DN for
      (&(objectCategory=person)(objectClass=user)(sAMAccountName=<id>)).
      Not found, or disabled in AD -> refused.
   5. BINDs as the user's own DN with the typed password.
      Accepted -> signed in (session cookie, 10 h). Rejected -> refused.
   6. DC unreachable / misconfigured -> "The company directory could not be
      reached" (HTTP 503) - never reported as a wrong password.
  Passwords are never stored, logged or sent unencrypted. Plain ldap:// without
  StartTLS is refused by the application. The user ID is escaped before
  searching (no LDAP injection).

9.4  AUTH_MODE
  local   everyone signs in with a local password (demo / before AD is ready)
  ad      only AD accounts can sign in
  hybrid  AD accounts via AD, local accounts via their password  <- USE THIS
          keeps the break-glass admin (5.5) working if a directory is down.

9.5  CONFIGURATION (.env) - one block per directory
        AUTH_MODE=hybrid
        AD_DIRS=ESL,IOB

        AD_ESL_URL=ldaps://<<esl DC FQDN>>:636
        AD_ESL_BASE_DN=<<e.g. DC=esl,DC=local>>
        AD_ESL_BIND_DN=<<CN=svc_visl_pmo,OU=Service Accounts,DC=esl,DC=local>>
        AD_ESL_BIND_PASSWORD=<<set me>>
        AD_ESL_CA_FILE=certs/esl-root-ca.pem
        AD_ESL_UNITS=ESL

        AD_IOB_URL=ldaps://<<iob DC FQDN>>:636
        AD_IOB_BASE_DN=<<e.g. DC=iob,DC=local>>
        AD_IOB_BIND_DN=<<CN=svc_visl_pmo,OU=Service Accounts,DC=iob,DC=local>>
        AD_IOB_BIND_PASSWORD=<<set me>>
        AD_IOB_CA_FILE=certs/iob-root-ca.pem
        AD_IOB_UNITS=IOB,FACOR
  Optional per directory: AD_<KEY>_STARTTLS=true (with ldap://dc:389),
  AD_<KEY>_USER_FILTER (default above), AD_<KEY>_UPN_SUFFIX (direct-bind mode
  when no service account is issued - user binds as id@suffix).
  AD_TIMEOUT_MS=10000. Create a folder "certs" in the application folder for
  the CA files. Tip: use a DNS name that resolves to several DCs (the domain
  name itself, e.g. esl.local, often does) rather than one DC's name, so the
  loss of one DC does not stop sign-in - but the name must be on the DC
  certificates (ask the AD team).

9.6  WHAT TO REQUEST FROM EACH AD TEAM (one ticket for ESL, one for IOB)
  ----------------------------------------------------------------------
  Subject: LDAPS service account for VISL EBITDA Drive PMO (read-only)
  1. A service account, e.g. svc_visl_pmo, in the <<ESL | IOB>> domain:
       - member of Domain Users only; NO admin rights, NO interactive logon
       - "Password never expires" (rotated manually on schedule) or per policy
       - read access to user objects under the base DN (default for Domain Users)
     Please send: its full Distinguished Name, and the password via the vault.
  2. The LDAPS endpoint: DC host name(s) or domain DNS name, port 636
     (confirm LDAPS is enabled and the DC certificate is valid for that name).
  3. The base DN that contains all staff who will use the application
     (e.g. DC=iob,DC=local or OU=Staff,DC=iob,DC=local).
     IOB team: confirm FACOR staff are within this base DN.
  4. The Root CA (and intermediate) certificate that issued the DC
     certificates, exported as Base-64 X.509 (.cer / PEM).
  5. Firewall: allow TCP 636 from application server <<IP/host>> to the DCs.
  6. Confirm users log on with sAMAccountName (e.g. firstname.lastname).
  ----------------------------------------------------------------------

9.7  EXPORTING THE ROOT CA CERTIFICATE (if the AD team asks how)
  On any domain-joined Windows PC: certlm.msc (or certmgr.msc) > Trusted Root
  Certification Authorities > Certificates > the company root CA > All Tasks >
  Export > "Base-64 encoded X.509 (.CER)". Save as certs/esl-root-ca.pem or
  certs/iob-root-ca.pem (renaming .cer to .pem is fine - it is the same text
  format beginning "-----BEGIN CERTIFICATE-----"). If there is an
  intermediate CA, paste it below the root in the same file.

9.8  TESTING - BEFORE ANY USER TRIES TO SIGN IN
  On the application server, in the application folder:
        npm run ad:test
            -> for each directory: config, TLS connection, service-account bind
        npm run ad:test -- --dir ESL --user <<an ESL person>>
            -> finds the person, shows DN / email / disabled flag
        npm run ad:test -- --dir IOB --user <<a FACOR person>> --password
            -> prompts for that person's password (hidden) and tests it
  Each step prints OK or FAIL with the likely cause. Then in the app:
  create that person as an AD user (5.4) and sign in.

9.9  AD TROUBLESHOOTING (ad:test translates these)
  Host name does not resolve        DNS from the app server; use the FQDN
  Connection refused / timed out    firewall TCP 636, or LDAPS not enabled on DC
  TLS certificate not trusted       wrong/missing CA file (9.7)
  Certificate name mismatch         use the exact name on the DC certificate
  Invalid credentials (49) at the service bind    wrong AD_<KEY>_BIND_DN or password
  No such object (32)               base DN or bind DN misspelt
  User not found                    wrong base DN (user outside it) or filter
  AD data 52e   wrong password        data 532  password expired
  data 533      account disabled      data 701  account expired
  data 773      must change password  data 775  account locked
  "Incorrect user ID or password" but ad:test passes   the user is not in the
      app, is inactive, is not marked Active Directory, or AUTH_MODE=local.
  "Company directory could not be reached" (503)   the directory for that
      user's home unit is down or misconfigured - run ad:test --dir <KEY>.

  enable ARR proxy (IIS > server > ARR Cache > Server Proxy Settings > Enable

  rewrite rule: match (.*) -> http://localhost:4010/{R:1}; preserve host
  header; add server variable X-Forwarded-Proto = https. Set the proxy
  timeout to 120 s.
  Linux / nginx:
        location / {
            proxy_pass http://127.0.0.1:4010;
            proxy_set_header Host $host;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
            proxy_read_timeout 120s;
        }
  Then COOKIE_SECURE=true and restart the service.
